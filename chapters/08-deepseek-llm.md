# DeepSeek LLM：先研究扩展规律，再扩大模型

论文：DeepSeek LLM: Scaling Open-Source Language Models with Longtermism（2024）

## 01 · 先研究怎样扩大模型

继续。这篇是 2024 年 1 月的《DeepSeek LLM: Scaling Open-Source Language Models with Longtermism》。如果按照你刚才读的顺序，它其实应该放在 DeepSeek-V2 和 V3 **之前**。而且这篇很重要，因为 V2/V3 已经开始讲 MLA、MoE、FP8、降低每个 token 的成本，但这一篇还在回答一个更加基础的问题：**如果我们准备长期不断把模型做大，到底应该怎么扩大？钱增加以后，是多造一些参数，还是让模型多读一些数据？学习率和 batch size 应该怎么跟着变化？更关键的是，我们能不能先拿小模型做实验，然后预测那个昂贵的大模型最后会有多强？**所以这篇论文的真正主角不是 DeepSeek LLM 67B 本身，而是 **Scaling Law——扩展定律**。作者最终训练了 7B 和 67B 两个主要模型，在约 2 万亿 token 上预训练，并发现 67B 在代码、数学、推理等多个 benchmark 上超过 LLaMA-2 70B。([arXiv][1])

## 02 · 算力应该分给模型，还是数据？

先用一个最简单的比喻理解 scaling law。假设你有 100 万预算培养一个学生，钱可以花在两个地方：第一，把“大脑”造得更大，也就是增加模型参数；第二，让他读更多书，也就是增加训练 token。现在预算涨到 1000 万，你应该怎么办？把大脑扩大 10 倍、书不增加？还是大脑不变、书增加 10 倍？还是两边一起增加？这不是一个小问题，因为训练一次几十亿、几百亿参数的大模型已经很贵，你不可能每一种组合都真的训练一次看看。Scaling law 想做的事情就是：**先用一堆便宜的小模型实验，找到“模型大小、数据量、计算量、最终 loss”之间的数学规律，然后拿这条规律去指导真正昂贵的大模型训练。**DeepSeek 把训练计算量粗略写成 \(C=M\times D\)，其中 \(D\) 是训练 token 数，\(M\) 是每处理一个 token 所需要的非 embedding FLOPs。于是问题就变成：当 \(C\) 增大时，怎样分配 \(M\) 和 \(D\) 才最划算？([arXiv][2])

这里你会碰到大模型历史里一个很重要的争论。早期 OpenAI 的 Kaplan scaling law 和后来 DeepMind 的 Chinchilla 给出了不太一样的答案。非常粗略地说，早期很多模型倾向于“模型做得很大，但数据相对没有那么多”；Chinchilla 后来发现很多大模型其实 **undertrained**——大脑造得太大，书却没读够，同样计算预算下，不如训练一个稍小但读更多数据的模型。DeepSeek 的作者于是问：为什么不同研究算出来的最佳比例不一样？他们认为其中一个重要原因是：**scaling law 并不是脱离训练条件存在的自然常数。数据质量、模型结构、超参数都会影响你测出来的规律。**特别是他们后来发现，不同质量的数据甚至会改变“新增算力应该更多花在模型还是数据”这个答案。([arXiv][2])

## 03 · 数据质量会改变最优配方

这件事特别值得理解。假设学生读的书质量很差，全是重复网页、垃圾文本、错误信息，那么让他多读一亿页，收益可能很低；这时候也许扩大模型没有意义，因为你只是在给一个更大的大脑灌垃圾。反过来，如果教材质量非常高，每一页信息密度都很大，那么一个太小的大脑可能反而吃不下这些知识，于是增加模型容量更划算。DeepSeek 实验得到的一个重要结论就是：**数据质量越高，随着计算预算增加，最佳策略会倾向于把更多新增计算资源分配给模型规模。**作者甚至提出一个很有意思的反向用途：也许可以观察一份数据产生的 scaling behavior，间接判断这批数据到底有多好。([arXiv][2])

## 04 · 去重与高质量数据

所以他们非常重视数据清洗。最终预训练数据大约 **2 万亿 token，以中文和英文为主**。数据处理大致经过 deduplication、filtering、remixing 三步。Deduplication 就是去重复：互联网看起来巨大，实际上同一篇文章可能被转载成百上千份，如果全部喂给模型，模型不是在获得新知识，而是在反复背同一页。作者发现，如果只在一次 Common Crawl dump 内去重，大约去掉 22.2%；但把 91 个 dumps 放在一起全局去重，去重率竟达到 **89.8%**。([arXiv][2]) 这个数字非常直观地告诉你：**“抓了多少 TB 网页”跟“真正获得多少独特训练信息”完全不是一回事。**所以到了现代 LLM，数据工程已经不是“多下载点网页”，而是决定模型能力的重要组成部分。

## 05 · Tokenizer 也是效率设计

Tokenizer 也很有意思。DeepSeek LLM 使用 byte-level BPE，词表大约 10 万个常规 token，并针对中文、日文、韩文字符等做了预分词处理，还把数字拆成单独的 digit。([arXiv][2]) 这里不用背实现，只要理解一个概念：tokenizer 就像模型读书之前的“切词方法”。同一句“人工智能正在发展”，你可以把它切成“人工 / 智能 / 正在 / 发展”，也可能切得更碎。如果一个 tokenizer 对英文特别高效、对中文却总要拆成很多 token，那么同样一个 4096-token context window，中文实际能放进去的信息就更少。所以对于一个中英双语都非常重要的模型，tokenizer 本身也是效率设计的一部分。

## 06 · 成熟架构与更深的网络

模型架构这一代其实还非常“传统”。DeepSeek LLM 大体沿用 LLaMA：decoder-only Transformer、RMSNorm、SwiGLU、RoPE。7B 是 30 层、隐藏维度 4096、32 个 attention heads；67B 则是 **95 层、隐藏维度 8192、64 个 attention heads**，上下文长度都是 4096。67B 为了降低推理成本已经用了 GQA，也就是 Grouped-Query Attention，让多个 query heads 共用较少的 Key/Value heads；它有 64 个 query heads，但只有 8 个 KV heads。([arXiv][2]) 这点特别有历史感，因为你刚刚读完 DeepSeek-V2：V1 时代他们还在用 GQA 减少 KV cache，到了 V2 就会认为“还不够省”，然后发明 MLA，把 KV 进一步压缩成 latent representation。所以你现在是在看到 MLA 出现以前的问题现场。

67B 还有一个很有意思的选择：他们更倾向于把参数增加到**深度**，而不是简单把 FFN 做得越来越宽。所以 67B 做到了 95 层。([arXiv][2]) 用费曼法理解就是：假设总共允许你花 67B 参数，你可以造一个“楼层少但每层特别宽”的大楼，也可以造一个“楼层很多但每层相对没那么宽”的大楼。DeepSeek 选择更深的结构，一方面基于性能实验，另一方面也考虑训练和推理时怎样进行 pipeline partition。这里已经能看到后来 DeepSeek 很鲜明的一种研究风格：**模型结构不是脱离硬件独立设计的，GPU 怎么切、怎么通信、怎么部署，也会反过来影响网络怎么造。**

## 07 · 超参数也需要随规模变化

但整篇论文真正值得认真读的是第三章。作者觉得过去 scaling law 有一个隐藏问题：你训练很多不同大小的小模型去拟合规律，可如果每个小模型的学习率和 batch size 本身就没有调好，那么你得到的 scaling law 可能是在比较“一堆没有发挥正常水平的学生”。所以他们先研究了一个更底层的问题：**模型变大以后，最佳 learning rate 和 batch size 怎么变？**实验发现随着计算预算增加，最佳 batch size 总体增大，而最佳 learning rate 总体减小。他们甚至拟合出了经验幂律关系。([arXiv][2]) 不需要背公式，记住思想就够了：**Scaling 不只是参数和数据一起变，训练方法本身也应该随着规模变化。**

这就像研究“人长高以后跑步速度怎么变化”，你不能让 5 岁小孩穿合脚鞋、成年人却穿小两码的鞋，然后根据比赛结果总结身高规律。你首先要保证每个规模都在相对合理的训练条件下，再比较它们。DeepSeek 因此先找每个计算规模附近的近似最佳超参数区域，然后才去拟合 model/data scaling law。这个步骤看起来没有 MoE、MLA 那么性感，但对于真正花几百万美元训练模型的人非常重要，因为 **scaling law 的价值不是事后解释曲线，而是训练大模型之前帮助你下注。**

## 08 · 用实际计算量衡量模型规模

作者还认为单纯用“参数数量”描述模型规模并不够准确，于是使用 **non-embedding FLOPs per token** \(M\) 来表示模型规模。原因很好理解：两个同样 7B 参数的 Transformer，如果层数、attention、词表等设计不同，每处理一个 token 真正执行的计算并不完全一样。过去常用 \(C\approx6ND\)，其中 \(N\) 是参数数量；DeepSeek 更倾向于写成 \(C=MD\)，直接考虑模型每 token 实际需要的非 embedding 计算。([arXiv][2]) 用费曼法说：**不要只数汽车有多少零件，最好直接看它每公里实际消耗多少能量。**这样比较不同模型结构时，尺度更接近真正的计算成本。

## 09 · 用小模型预测大模型

有了这些小模型实验以后，真正有意思的事情发生了：他们用 scaling law **提前预测 DeepSeek LLM 7B 和 67B 的最终表现**，然后真的训练这两个大模型，发现预测和最终结果能够较好对应。([arXiv][2]) 这件事情和你之前读 GPT-4 Technical Report 时看到的 predictable scaling 是同一种思想：大模型训练贵到不能随便试错以后，“预测模型训练结果”本身变成了一门非常重要的技术。你可以把小模型叫作风洞实验：造真正的波音飞机以前，不会先造十架完整飞机试哪个机翼好，而是先做大量小规模实验，再根据规律决定最终设计。

## 10 · 为持续训练设计学习率

预训练时他们还做了一个看起来很小、但很符合“longtermism”标题的选择：不用最常见的 cosine learning-rate decay，而采用 **multi-step learning-rate scheduler**。原因不是 cosine 不好——实验里最终性能其实差不多——而是 multi-step 更方便 **continual training**。([arXiv][2]) 假设今天只有 2T token，明年收集到 4T token。如果学习率早已经沿 cosine 一路衰减到接近零，继续训练比较麻烦；multi-step 则更容易保留前一阶段训练结果，再接着扩数据。这就是标题里 “Longtermism” 真正的味道：作者不是把 67B 当作一次性的终点，而是在问**如果以后还要继续增加数据、增加模型、增加算力，现在的训练方法应该怎样方便未来扩展？**

## 11 · SFT 与 DPO：从模型到助手

模型预训练完以后，故事就进入你已经熟悉的 post-training。作者收集了超过 **100 万条 SFT 数据**，覆盖有帮助性和安全相关内容，然后训练 DeepSeek Chat。之后又使用 **DPO，Direct Preference Optimization** 继续做偏好对齐。([arXiv][1]) DPO 可以用非常简单的方式理解：给模型同一个问题的两个答案，一个人类更喜欢，一个不喜欢，然后直接训练模型让“好答案”的概率相对于“差答案”变大。它和传统 RLHF 的目标相似——让模型更符合人的偏好——但不需要先训练一个 reward model，再用 PPO 跑一整套强化学习流程，因此更加直接。注意这个时间点 DeepSeek 还在用 DPO；到了你刚刚读的 V2，他们就会进一步转向 **GRPO**，这也是 DeepSeek 技术路线继续演化的一个清楚节点。

## 12 · 评测结果与比较的边界

最终结果方面，DeepSeek LLM 67B 在作者评测的多个 benchmark 上超过 LLaMA-2 70B，尤其是**代码、数学和推理**任务；经过 SFT 和 DPO 的 67B Chat，在论文当时的中英文开放式评测中也表现很强，作者报告其评测结果超过 GPT-3.5。([arXiv][1]) 但和前面一样，别把“超过 GPT-3.5”读成一个永久有效的总体智力排名：这是特定时间、特定版本和特定评测设置下的结果。论文真正需要你记住的不是排行榜，而是：**他们通过小规模 scaling 实验决定 7B/67B 怎么训练，再真的把预测落实成了有竞争力的大模型。**

## 13 · 从 DeepSeek LLM 到 V3

现在你可以把 DeepSeek V1 → V2 → V3 连起来看了，这条路线其实非常漂亮。**DeepSeek LLM/V1：先研究 scaling law，回答“模型应该怎么科学地变大”；DeepSeek-V2：模型继续扩大以后，发现 dense model 每 token 太贵、KV cache 太大，于是引入 DeepSeekMoE 和 MLA，回答“怎么让大模型便宜运行”；DeepSeek-V3：继续保留 MoE + MLA，再加入 FP8、MTP、auxiliary-loss-free balancing、DualPipe 等，把问题推进到“怎样把超大 MoE 的每一单位算力利用到极致”。**所以 V2、V3 并不是突然出现的几个工程技巧，它们背后的研究哲学其实已经写在 V1 的标题里了：**Longtermism——不要只追求这一代 benchmark，而要研究一套可以持续扩大模型的系统方法。**

更有意思的是，把它和你之前读的 GPT 系列并排，会发现两条历史线关注点不同。GPT-1 → GPT-2 → GPT-3 的核心问题越来越接近：**next-token prediction 到底会自然产生多少通用智能？**GPT-4 又加入了多模态、对齐和安全。而 DeepSeek 从这一篇开始特别鲜明地加入另一条问题线：**既然 scaling 有效，我们怎样理解 scaling、预测 scaling，然后把 scaling 做得越来越经济？**所以 DeepSeek 后来的 MoE、MLA、FP8 并不是零散的“省钱技巧”，而可以看成这个问题的连续答案。

## 14 · 用一分钟讲给朋友听

如果现在把论文合上，用费曼法一分钟讲给朋友听，我会这样说：**DeepSeek LLM 这篇论文真正研究的是“造大模型之前能不能先算明白怎么造”。作者先训练很多小模型，研究计算预算增加时学习率、batch size、模型规模和数据规模应该怎样变化，然后用这些 scaling law 去指导真正的 7B 和 67B 模型。他们还发现 scaling law 会随着数据质量变化：数据越好，新增计算预算越值得分给更大的模型。这说明 scaling law 并不是一条脱离数据存在的万能公式。最后，他们用约 2 万亿中英文 token 训练 DeepSeek LLM，再通过超过 100 万条 SFT 数据和 DPO 做成聊天模型，67B 在代码、数学、推理等多个测试上超过 LLaMA-2 70B。**([arXiv][1])

所以这一篇我建议你只留下一个公式般的思想：**先测 Scaling Law，再花 Scaling Money。**📖 不要先砸巨额算力然后祈祷模型变聪明，而是先用小实验回答：**预算增加以后，模型应该大多少、数据应该多多少、学习率应该多大、batch 应该多大、最终 loss 大概会是多少。**而一旦你把 V1、V2、V3 连起来，DeepSeek 的技术路线就非常清楚了：**V1 研究“怎么扩大”，V2 研究“怎么稀疏和压缩”，V3 研究“怎么把整个训练与推理系统的效率继续榨出来”。**这三篇其实可以当作连续三章来读。
